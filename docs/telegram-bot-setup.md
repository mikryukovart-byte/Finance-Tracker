# Telegram Actions и Work Records: настройка

Бот принимает текстовые и голосовые сообщения и различает три сценария:

- совершённые Daily Actions сохраняются в `DailyActionLog`;
- рабочие заметки, решения, идеи, риски и планы сохраняются как `WorkRecord`;
- свободные размышления сохраняются как `JournalEntry` только после подтверждения, после чего бот присылает короткую обратную связь.

Все три сценария всегда показывают черновик и требуют явного подтверждения перед сохранением. Команда «Превратить в действие» сначала создаёт обычный черновик Daily Action и также требует отдельного подтверждения.

Для Work Records сохраняется только краткая структурированная суть. Исходное аудио, Telegram voice file ID и полная сырая расшифровка не сохраняются в базе данных.

## 1. Переменные окружения Vercel

Добавьте в Vercel для нужных окружений и затем сделайте новый deploy:

```bash
TELEGRAM_BOT_TOKEN="токен от BotFather"
TELEGRAM_WEBHOOK_SECRET="случайная длинная строка для Telegram webhook"
TELEGRAM_ALLOWED_CHAT_ID="единственный разрешённый Telegram chat id"
TELEGRAM_TRACKER_USER_ID="Supabase Auth user id владельца трекера"
TELEGRAM_SETUP_SECRET="отдельная случайная длинная строка для setup route"
```

Также должен быть настроен существующий `OPENAI_API_KEY`. Серверная переменная `OPENAI_WORK_RECORD_MODEL` необязательна: если она отсутствует, разбор рабочих записей использует существующий `OPENAI_MODEL`. Не добавляйте префикс `NEXT_PUBLIC_` к этим переменным: все они должны оставаться серверными.

## 2. Создание бота

1. Откройте официальный чат `@BotFather` в Telegram.
2. Выполните `/newbot`, задайте имя и username.
3. Сохраните полученный токен в `TELEGRAM_BOT_TOKEN` в Vercel.
4. Никому не пересылайте токен и никогда не коммитьте его в git.

## 3. Получение chat ID

До настройки webhook отправьте боту `/start`, затем локально выполните запрос к `getUpdates`, не публикуя токен и вывод команды:

```bash
curl -s "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/getUpdates"
```

Возьмите числовое значение `message.chat.id` из собственного сообщения и запишите его в `TELEGRAM_ALLOWED_CHAT_ID`. После этого удалите локальный токен из истории shell, если вводили его непосредственно в команду. Для группового чата ID может быть отрицательным; сравнение выполняется как точная строка.

`TELEGRAM_TRACKER_USER_ID` — это UUID пользователя из Supabase Authentication → Users, которому уже принадлежат данные трекера. Бот никогда не принимает этот ID из Telegram update.

## 4. Миграция и webhook

Для подтверждений используются отдельные таблицы короткоживущих черновиков Daily Actions и Work Records. Существующая production-база была обновлена точным SQL из миграции `20260702150000_work_records` через:

```bash
npx prisma db execute --file prisma/migrations/20260702150000_work_records/migration.sql --schema prisma/schema.prisma
```

Это было сделано потому, что история Prisma migrations в существующей production-базе не baselined. Не используйте `prisma db push` для WorkRecord или RLS. Не запускайте `prisma migrate deploy`, пока история существующей базы сначала не будет намеренно и полностью baselined. Ничего не сбрасывайте.

Настройте webhook защищённым route, подставив production URL и передав setup secret только в заголовке:

```bash
curl -X POST "https://YOUR_DOMAIN/api/telegram/setup-webhook" \
  -H "x-telegram-setup-secret: $TELEGRAM_SETUP_SECRET"
```

Успешный безопасный ответ: `{"ok":true}`. Route регистрирует `https://YOUR_DOMAIN/api/telegram/webhook` и передаёт Telegram значение `TELEGRAM_WEBHOOK_SECRET` как `secret_token`. Токен бота в ответе не возвращается.

## 5. Проверка

1. Отправьте `/start` и проверьте вводную подсказку.
2. Отправьте действие: `Отправил КП бассейну AquaLeader, завтра напомню.`
3. Проверьте Daily Action черновик. До нажатия «Сохранить» записи в трекере быть не должно.
4. Нажмите «Отмена» и убедитесь, что действие не создано.
5. Повторите ввод, подтвердите сохранение и проверьте запись на странице `/strategy/actions`.
6. Отправьте рабочую заметку: `Входящих пока нет, поэтому ближайшие три дня лучше писать потенциальным клиентам.`
7. Проверьте WorkRecord черновик, отмену и подтверждённое сохранение на странице `/strategy/notes`.
8. Отправьте голосовое длительностью до 300 секунд и повторите проверки подтверждения и отмены. Убедитесь, что в БД остаются только `cleanedText`, структурные поля и feedback: аудио, voice file ID и исходная расшифровка нигде не отображаются и не сохраняются.
9. Для проверки ограничения отправьте голосовое длиннее 300 секунд: бот не должен транскрибировать его и должен попросить разбить мысль на несколько сообщений.
10. Отправьте свободное размышление, проверьте компактный preview Journal, затем отдельно Cancel и Save. Feedback должен приходить только после Save.

Для ежедневной обратной связи можно задать `OPENAI_DAILY_FEEDBACK_MODEL`. Цепочка fallback: `OPENAI_DAILY_FEEDBACK_MODEL` → `OPENAI_WORK_RECORD_MODEL` → `OPENAI_MODEL` → `gpt-4o-mini`. Для недельного отчета используется `OPENAI_WEEKLY_REPORT_MODEL` → `OPENAI_ADVISOR_MODEL` → `OPENAI_MODEL` → `gpt-4o-mini`.

Защищенный endpoint недельной доставки: `/api/cron/weekly-advisor`. Он принимает только `Authorization: Bearer <CRON_SECRET>`, проверяет сохраненные timezone/day/time и не создает повторный отчет за тот же недельный период. Расписание Vercel нужно включать отдельно после выбора частоты вызова; в репозитории оно намеренно не включено автоматически.

Черновики истекают через 30 минут. Не храните реальные токены в `.env.example`, документации, логах, issue или коммитах.
